# Бот-бухгалтер Изи

Я реализовал `decide(message, history) -> Decision` на Python 3.11+ без сторонних
Python-зависимостей. Я допускаю лишнюю передачу бухгалтеру, если не могу надёжно проверить запрос.

## Как я запускаю

Из корня репозитория я запускаю тесты:

```bash
python -X utf8 -m unittest discover -s tests -v
```

В тестах я подменяю модель и HTTP-ответы, а подключения через сокеты блокирую.
Ollama, интернет и ключи для этого не нужны. Я проверяю все 12 примеров подряд
в одном чате и дополнительные случаи: чужие ответы, цитаты, отрицания,
повторную доставку, подмену номера, выдуманные реквизиты, ошибки модели и конкуренцию.
Я проверил решение на Python 3.13.7: прошли 52 теста без сети и все 12 примеров
в отдельном прогоне с настоящей Qwen3 8B.

Для настоящей модели я использую [Ollama](https://ollama.com/) и
[Qwen3 8B](https://ollama.com/library/qwen3:8b). Я выбрал локальную модель, чтобы
не требовался платный API и сообщения не уходили внешнему провайдеру.
Я запрашиваю [JSON по схеме](https://docs.ollama.com/capabilities/structured-outputs)
через `/api/chat`, с `temperature=0` и `think=false`; затем самостоятельно проверяю ответ.

```bash
ollama pull qwen3:8b
# В отдельном терминале, если сервер ещё не запущен:
ollama serve
# Проверка 12 примеров с настоящей моделью:
python -X utf8 -m examples.smoke
```

Модель и адрес сервера я могу изменить через `OLLAMA_MODEL` и `OLLAMA_BASE_URL`
(по умолчанию `qwen3:8b` и `http://localhost:11434`). Таймаут запроса — 60 секунд.

Для ручного ввода я запускаю `python -X utf8 -m easybot`: программа читает по одному
JSON-сообщению на строку и печатает решение. Например, я ввожу последовательно:

```json
{"id":"1","author_id":"client-1","text":"Изи, выстави счёт"}
{"id":"2","author_id":"client-1","text":"Алтын Сауда, 5 000","reply_to":"izi:1"}
```

## Как я устроил решение

Я отделил классификатор (`easybot/llm.py`) от правил (`policy.py`), принятия решения
(`bot.py`) и данных (`ledger.py`). Модель выбирает умение и извлекает дословные
фрагменты реквизитов. Я не даю ей доступ к выполнению действий или формированию
денежных ответов.

В коде я проверяю обращение отдельным словом «Изи» либо ответ на активный вопрос
бота. Я исключаю цитаты и собственные сообщения бота. Для уточнения я проверяю
`reply_to`, чат и автора; соседнюю реплику не считаю ответом. Я задаю максимум один
вопрос: повторная нехватка данных, смена задачи или неопределённость ведут к бухгалтеру.
Новое обращение того же автора закрывает предыдущее уточнение, обычная беседа — нет.

Я проверяю схему ответа модели, наличие реквизитов в текущем запросе/уточнении,
однозначное совпадение покупателя со справочником, сумму и точный номер документа.
Кавычки, регистр и префикс «ТОО» я нормализую; опечатки не угадываю. Отдельными
проверками я отклоняю удаление, изменение, услуги бухгалтерской фирмы, отрицания,
несколько действий и противоречивые числа. Эти проверки могут только запретить
действие: без классификации LLM я умение не выбираю.

Деньги я храню в `Decimal`, в JSON возвращаю строками. Налоги суммирую из
`data.json`: **21 675 ₸**, остаток беру оттуда же: **552 314,17 ₸**. Новый счёт
получает `max(number) + 1`, поэтому в последовательности примеров появляются
№ 32 и № 33. При отправке я ищу строго запрошенный номер; отсутствующий документ
не заменяю похожим. Повтор одного `message.id` возвращает прежнее решение;
блокировкой защищаю создание счёта от одновременной повторной доставки.

## Как я вызываю функцию из кода

```python
from easybot import Message, Turn, decide

history = []
message = Message(id="1", author_id="client-1", text="Изи, сколько денег на счету?")
decision = decide(message, history)
history.append(Turn(message, decision))
print(decision.to_dict())
```

Для подмены модели я создаю `AccountantBot(model=FakeModel())` и вызываю его
`decide(message, history)`; пример подмены находится в `tests/helpers.py`.
Я считаю `history` полной хронологической историей доверенных объектов `Turn`,
а идентификаторы и роли — метаданными транспорта, а не текстом пользователя.
В интеграции я сопоставил бы `question_id` с реальным ID сообщения бота.
Один экземпляр обслуживает один клиентский чат; у функции по умолчанию это `demo`.

## Что я оставил за рамками

Я храню новые счета и защиту от повторов в памяти процесса: после перезапуска
загружается исходный `data.json`. Для эксплуатации я добавил бы постоянное
хранилище, транзакции и уникальный ключ доставки. Я не подключал мессенджер,
банк и генерацию PDF: `send_document` возвращает запись существующего счёта,
поскольку в задании нет файлов документов.

Я намеренно передаю бухгалтеру суммы прописью/с множителями, другую валюту,
сложные периоды и формулировки, которые не подтверждаются проверками.
Я не считаю регулярные выражения и JSON-схему полной защитой от смысловых ошибок
LLM; перед рабочим запуском я расширил бы проверку на обезличенной переписке.
Автотесты проверяют правила с подменённой моделью; отдельный smoke-прогон проверяет
живую модель и не доказывает качество на всех возможных сообщениях.
